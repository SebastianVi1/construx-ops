# The cost catalog is the licensee's own import: one per organization, merged by code, never shared

Status: proposed (2026-11-15). Supersedes ADR 0004 in part: Price observations become Cost history entries and the catalog widens from Materials to every Resource (Material, Labor category, Gang, Equipment rate, Work item).

Each organization has exactly one Catalog. It is filled by importing the Excel export of the cost database the company already licenses (Neodata ConstruBASE as exported by PU Win+: the Presupuesto workbook, plus the optional FASAR workbook) and by hand-made Resources. The first import creates the Catalog; every later import is a merge by Resource code: a dry run reports new, cost changed, unchanged and missing-from-file codes, and the confirmation writes a Cost history entry effective from now for each changed cost. Codes missing from the file are flagged, never deleted. Every imported row records its source (`NEODATA_CONSTRUBASE`), and the import job records the file key, its SHA-256, the uploader, the time, and the uploader's acceptance of the statement "I hold a valid licence for this catalog and import it for my company's internal use". Construx ships no seed catalog, never copies a Catalog between organizations and never shows one organization another's costs. The existing Material prices module (`modules/pricing`) is re-conceived as this Catalog rather than replaced: a Material is a Resource of type `MATERIAL`, a Supplier stays a Supplier, and the closed unit and category enums become per-organization Units and Families.

Why: the data is Neodata's, licensed per named user to the company, with no public EULA that would let Construx redistribute it. The only lawful and sustainable path is for each licensee to bring its own export, and the only place the import can legitimately land is that licensee's tenant. Merging by code keeps the company's hand edits and the Site data that points at Resources (labor rates, expenses) stable across yearly re-imports, which a fresh catalog per import would break. Keeping one module avoids two catalogs for the same material and a second "price" vocabulary in the UI.

Considered and rejected: attaching the ConstruBASE `.mdf` through SQL Server (a SQL Server 2019 LocalDB file with an undocumented schema and no Java reader; it would also tie the backend to a second database engine); one Catalog per import (versioning by whole copies breaks every reference from Sites and doubles 35 000 rows a year); keeping Materials as a separate module beside the imported catalog (two sources of truth for the same cement bag, two UIs); a Construx-provided shared catalog (no licence to redistribute, no curator, and it would leak negotiated costs between companies, the same reason ADR 0004 gave).

Consequences: a Resource's identity is its code, not its name; two Resources may share a name. Importing again overwrites descriptive fields and costs from the file, so a hand-edited cost is reported as "cost changed" and reverted unless the user skips the confirmation. The per-supplier price comparison of ADR 0004 (several Suppliers per Material, cheapest first) is gone: a Resource has one current Cost and its history keeps the Supplier of each entry. Only the current import format is supported; a Neodata export change is an import failure with a readable message, not a silent misread. The `.mdf` route, "Intercambio" files and other vendors are future import sources added beside this one, each needing its own ADR.
