# Roles and permissions: editable roles, custom roles, role assignment

Status: approved in the grilling session of 2026-11-22 (Q1 to Q29). ADR: `.agents/adr/0010-built-in-roles-editable-and-synced.md`.

Vocabulary (`GLOSSARY.md`): **Member**, **Organization role**, **Permission**, **Owner role**, **Built-in role**, **Custom role**. In code a Built-in role is `OrganizationRole.seeded = true` and the Owner role is `systemRole = true`; the UI never says "seeded". Company = `Organization`, Site = `Project`.

All paths are under `/api/organizations/{organizationId}` unless they start with `/api/permissions`. Every unsafe request needs the CSRF header, as today. Errors use the existing `ProblemDetail` shape with a `code` property.

## 1. Decisions

| # | Decision |
|---|---|
| D1 | Allow-list only. A role grants (action, scope) pairs; anything not granted is denied. There is no explicit deny. (Q1) |
| D2 | Each member holds exactly one role. No per-member overrides. (Q4) |
| D3 | The Owner role is locked: never edited, never assigned, never removed, and it always holds every action at `ORGANIZATION`. (Q2) |
| D4 | Built-in roles are editable per company (permissions only) and can be restored to the defaults. They cannot be renamed in the app or deleted. (Q2, Q12, Q14, Q17) |
| D5 | Custom roles: created blank or by duplicating any role the caller may duplicate, unique name of 1 to 100 characters, optional description up to 280 characters, at most 30 per company. (Q7, Q14, Q16) |
| D6 | Scopes per action come from the permission catalog. The editor offers None / Own tasks / Assigned sites / Whole company, filtered to the allowed scopes. (Q5, Q26) |
| D7 | "Never above your own role" (Q3, Q9, Q10, Q11, Q18), see §3. |
| D8 | Dependencies are enforced by the backend, and the editor switches them on automatically (Q20), see §4. A role with no permissions is valid. (Q21) |
| D9 | Changes take effect on the member's next request, with no notification. Every change is audited. (Q15) |
| D10 | Built-in roles and the permission catalog are defined once in the backend. A startup sync applies them to every company (Q23 to Q27), see §6. Flyway backfills of role grants are no longer written. |
| D11 | Codes are permanent ids: role codes (`WORKER`, `CUSTOM_…`) and action codes (`MANAGE_PLAN`). Only display names change. (Q27) |
| D12 | The 16 existing actions are the catalog. Splitting actions is out of scope. (Q6) |

## 2. Data model changes (migration `V41__editable_roles.sql`)

`organization_role` gains:

| Column | Type | Meaning |
|---|---|---|
| `description` | `varchar(280)` null | Custom roles only. Built-in descriptions come from the definition file. |
| `customized` | `boolean not null default false` | Built-in role whose permissions the company changed. Cleared by restore. |
| `version` | `bigint not null default 0` | Optimistic lock (`@Version`). |

New table `organization_role_known_action (role_id uuid not null references organization_role(id) on delete cascade, action varchar(40) not null, primary key (role_id, action))` records which catalog actions a Built-in role has already been reconciled against (§6). It must run on PostgreSQL and on H2 in `MODE=PostgreSQL`: no arrays, no `ON CONFLICT`.

Custom role codes are generated by the server: `CUSTOM_` followed by 10 uppercase base-32 characters (`[A-Z2-7]`). Built-in codes in the definition file may not start with `CUSTOM_`, and the file loader fails at startup if one does. The two code sets therefore never collide.

Role names: a custom role name may not equal (case-insensitive, trimmed) another role's stored name in the company (`uk_role_org_name`, as today) or the EN or ES name of any Built-in role in the definition file. Built-in roles keep a stored `name` (the ES name, as today) for database readability only. The API takes display names from the definition file.

## 3. Authority rules ("never above your own role")

Scope order: `OWN` < `PROJECT` < `ORGANIZATION`. Role **A fits within** caller **C** when, for every grant (action, s) of A, C's role holds that action at a scope ≥ s. The Owner role fits within no one but Owner, so in practice only an Owner can change an Owner.

| Operation | Permission needed | Extra rules (in order) |
|---|---|---|
| Read the roles list or one role | `MANAGE_ROLES` or `MANAGE_MEMBERS` (`ORGANIZATION`) | none |
| Create a custom role | `MANAGE_ROLES` | The new permission set fits within the caller. |
| Edit a role's permissions, name or description | `MANAGE_ROLES` | Not the Owner role (`ROLE_OWNER_LOCKED`). Not the caller's own role (`ROLE_OWN`). The role as it stands **and** the new set both fit within the caller (`ROLE_ABOVE_CALLER`). |
| Restore defaults (Built-in only) | `MANAGE_ROLES` | Same as edit, checked against the current set and the default set. |
| Delete a custom role | `MANAGE_ROLES` | Same as edit, plus a replacement when the role is held (§5.6). |
| Assign a member to a role | `MANAGE_MEMBERS` | Not yourself (`ROLE_OWN`). Not the Owner role, as target or as current role (`ROLE_OWNER_LOCKED`). The member's current role and the target role both fit within the caller (`ROLE_ABOVE_CALLER`). |
| Invite with a role | `MANAGE_MEMBERS` | The role is not the Owner role and fits within the caller (`ROLE_ABOVE_CALLER`). |

The dashboard receives the result of these rules per role as `editable` and `assignable` booleans (§5.1), so it never recomputes them.

## 4. Permission rules (validated on every write, and on the definition file at startup)

1. Each (action, scope) must be allowed by the catalog (`ROLE_SCOPE_INVALID`). The allowed scopes reproduce today's `Permission.validate`:
   - `MANAGE_ORGANIZATION`, `MANAGE_ROLES`, `MANAGE_MEMBERS`, `VIEW_PRICES`, `MANAGE_PRICES`, `VIEW_BUDGET`, `MANAGE_BUDGET`: `ORGANIZATION` only.
   - `VIEW_PROJECT`, `MANAGE_PROJECT`, `VIEW_GOAL`, `MANAGE_GOAL`, `ASSIGN_ACTIVITY`, `VIEW_PLAN`, `MANAGE_PLAN`: `PROJECT` or `ORGANIZATION`.
   - `VIEW_ACTIVITY`, `MANAGE_ACTIVITY`: `OWN`, `PROJECT` or `ORGANIZATION`.
2. Requirements (`ROLE_DEPENDENCY_MISSING`, with properties `action` and `requires`). `X ≥ s` means the role holds X at scope ≥ s.

   | Grant at scope s | Requires |
   |---|---|
   | `MANAGE_PROJECT` | `VIEW_PROJECT ≥ s` |
   | `VIEW_GOAL`, `MANAGE_GOAL`, `VIEW_ACTIVITY`, `MANAGE_ACTIVITY`, `ASSIGN_ACTIVITY`, `VIEW_PLAN`, `MANAGE_PLAN` | `VIEW_PROJECT ≥ max(s, PROJECT)` |
   | `MANAGE_GOAL` | `VIEW_GOAL ≥ s` |
   | `MANAGE_ACTIVITY`, `ASSIGN_ACTIVITY` | `VIEW_ACTIVITY ≥ s` |
   | `MANAGE_PLAN` | `VIEW_PLAN ≥ s` |
   | `MANAGE_PRICES` | `VIEW_PRICES` |
   | `MANAGE_BUDGET` | `VIEW_BUDGET` |

   All current Built-in roles and the Owner role satisfy these rules (checked against `seeded-roles.properties` on 2026-11-22).
3. An action appears at most once in a set (`ROLE_SCOPE_INVALID`).
4. An empty set is valid.

## 5. Endpoints

### 5.1 `GET /roles` (changed)

Access: `MANAGE_ROLES` or `MANAGE_MEMBERS` (today: `MANAGE_MEMBERS` only). Ordered Owner, then Built-in roles in file order, then custom roles by name.

```json
[{
  "id": "uuid",
  "code": "WORKER",
  "kind": "BUILT_IN",
  "name": "Trabajador",
  "names": { "en": "Worker", "es": "Trabajador" },
  "description": { "en": "Field staff: sees their sites, updates own tasks.", "es": "…" },
  "system": true,
  "customized": false,
  "memberCount": 12,
  "pendingInvitationCount": 1,
  "editable": true,
  "assignable": true,
  "version": 3
}]
```

- `kind` is `OWNER` | `BUILT_IN` | `CUSTOM`.
- For `CUSTOM`, `names.en` and `names.es` both equal `name`, and `description.en` and `description.es` both equal the stored description (or both are null).
- `system` stays for backward compatibility: true for `OWNER` and `BUILT_IN`. It means "name is fixed", not "permissions are fixed".
- `memberCount` counts `ACTIVE` and `SUSPENDED` memberships.
- _As shipped:_ `pendingInvitationCount` counts invitations with status `PENDING`, expired ones included (as in the invitations list).
- `editable` and `assignable` apply §3 for the caller. `assignable` is false for Owner and for any role the caller cannot assign or invite into.

### 5.2 `GET /roles/{code}` (new)

Access as 5.1. Returns the 5.1 object plus:
- `permissions`: `[{ "action": "VIEW_PLAN", "scope": "PROJECT" }]` in catalog order.
- `defaults`: the definition-file set, for `BUILT_IN` only (so the UI can preview "Restore defaults"). Null otherwise.
- _As shipped (review fixes):_ `formerMemberCount` (memberships with status `LEFT`) and `invitationCount` (invitations in any status), the same counts §5.6 reports, so the delete dialog can show everything that moves before the first `DELETE` (story 24). The list (§5.1) does not carry them.

404 `NOT_FOUND` for an unknown code.

### 5.3 `POST /roles` (new)

```json
{ "name": "Foreman with prices", "description": "optional", "permissions": [{ "action": "VIEW_PROJECT", "scope": "PROJECT" }] }
```

Returns 201 with the 5.2 body. "Duplicate" is done by the dashboard: it pre-fills this request from the source role's 5.2 body with the name "<name> (copy)" / "<name> (copia)". Errors: `ROLE_NAME_INVALID` 400, `ROLE_NAME_TAKEN` 409, `ROLE_LIMIT_REACHED` 409 (30 custom roles), `ROLE_SCOPE_INVALID` 400, `ROLE_DEPENDENCY_MISSING` 400, `ROLE_ABOVE_CALLER` 403.

### 5.4 `PUT /roles/{code}` (new)

```json
{ "name": "…", "description": "…", "permissions": [ … ], "version": 3 }
```

Replaces the full permission set. For `BUILT_IN`, `name` and `description` must be absent (`ROLE_NAME_FIXED` 400), and a change sets `customized = true`; a PUT that results in exactly the defaults sets `customized = false`. Errors: those of 5.3, plus `ROLE_OWNER_LOCKED` 400, `ROLE_OWN` 403, `ROLE_CHANGED` 409 (stale `version`). Returns 200 with the 5.2 body.

_As shipped (#107):_ for a `CUSTOM` role, `name` and `description` travel together. A body with `name` renames the role and sets the description to what it carries (null or blank clears it); a body with only `description` sets it; a body with neither keeps both. Every successful PUT raises `version`, even a no-op.

### 5.5 `POST /roles/{code}/restore-defaults` (new)

Body `{ "version": 3 }`. `BUILT_IN` only (`ROLE_NOT_BUILT_IN` 400). Sets the permissions to the defaults, sets `customized = false`, and marks every catalog action as known. Authority as 5.4. Returns 200 with the 5.2 body.

### 5.6 `DELETE /roles/{code}?replacement={code}` (new)

`CUSTOM` only (`ROLE_BUILT_IN_UNDELETABLE` 400; the Owner role gets `ROLE_OWNER_LOCKED`). A replacement is required whenever any membership (`ACTIVE`, `SUSPENDED` or `LEFT`) or any invitation (any status) still references the role, because the foreign keys need a role. Without one the call fails with `ROLE_REPLACEMENT_REQUIRED` 409, with properties `memberCount` (active + suspended), `formerMemberCount` (left) and `pendingInvitationCount`. _As shipped (#107):_ the 409 also carries `invitationCount` (invitations of any status), which explains a 409 where the three named counts are 0. The replacement must be another role of the company, not the Owner role, and assignable by the caller (`ROLE_REPLACEMENT_INVALID` 400 / `ROLE_ABOVE_CALLER` 403). Assignable needs `MANAGE_MEMBERS`, so deleting a role that is still referenced needs `MANAGE_MEMBERS` as well as `MANAGE_ROLES` (without it the call is `FORBIDDEN` 403); an unreferenced role needs only `MANAGE_ROLES`. The dashboard hides Delete for a referenced role when the caller lacks `MANAGE_MEMBERS`. Every referencing membership and invitation moves to the replacement in the same transaction, then the role is deleted. Returns 204. The caller can never be among the moved members, because deleting your own role is already `ROLE_OWN`. _As shipped:_ a `replacement` sent for an unreferenced role is still validated, and delete takes no `version`.

### 5.7 `GET /members?status=…&role={code}` (changed)

Adds an optional `role` filter for the People tab. Access unchanged (`MANAGE_MEMBERS`). _As shipped:_ a blank `role` means no filter; an unknown code returns `[]`, not 404.

### 5.8 `PATCH /members/{membershipId}` (changed)

Same body (`{ "roleCode": "…" }`). Adds the §3 assignment rules. The existing "own role" denial becomes `ROLE_OWN` 403; owner cases become `ROLE_OWNER_LOCKED` 400.

### 5.9 `POST /invitations` (changed)

Adds the §3 invitation rule (`ROLE_ABOVE_CALLER` 403). _As shipped:_ inviting as the Owner role is `ROLE_OWNER_LOCKED` 400 (was `INVALID_ARGUMENT`); an unknown role stays 404.

### 5.10 `GET /api/permissions/catalog` (new, not company-scoped)

Access: any authenticated user. The response is static per deploy and can be cached by the client for the session.

```json
{
  "groups": [{ "key": "PLANS", "names": { "en": "Plans", "es": "Planos" } }],
  "actions": [{
    "action": "MANAGE_PLAN",
    "group": "PLANS",
    "names": { "en": "Edit plans", "es": "Editar planos" },
    "descriptions": { "en": "Upload, calibrate and draw zones on site plans.", "es": "…" },
    "scopes": ["PROJECT", "ORGANIZATION"],
    "requires": [{ "action": "VIEW_PLAN", "minScope": "SAME" }, { "action": "VIEW_PROJECT", "minScope": "PROJECT" }]
  }]
}
```

- `minScope` is `SAME` (≥ the granted scope), `PROJECT` (≥ max(granted, PROJECT)) or `ORGANIZATION`.
- Groups in order: `COMPANY` (organization, roles, members), `SITES`, `PHASES`, `TASKS`, `PRICES`, `BUDGETS`, `PLANS`.
- Every action has EN and ES names and descriptions. A startup check fails the boot if any is missing.

### 5.11 Role summaries everywhere gain `names`

Every response object that carries a role summary `{ code, name }` gains `names: { en, es }`, resolved as in 5.1. This covers:
- `GET /me` → `role`
- `GET /api/organizations` and `GET /api/organizations/{id}` → `myRole`
- `GET /members` → `role`
- invitations → `role`
- any Site people/access response that includes a role

Members without `MANAGE_ROLES` or `MANAGE_MEMBERS` (who cannot read `GET /roles`) therefore still see the right name in their language. One helper (`RoleNames.of(OrganizationRole)`) builds it. The Owner role's names (`Owner` / `Propietario`) live in the definition file under `owner:`, so they are editable the same way, but its permissions are not.

### 5.12 Error codes

| Code | Status | When |
|---|---|---|
| `ROLE_ABOVE_CALLER` | 403 | §3: the role or permission set does not fit within the caller |
| `ROLE_OWN` | 403 | Editing your own role, or changing your own assignment |
| `ROLE_OWNER_LOCKED` | 400 | Any write that targets the Owner role, or assigns into or out of it |
| `ROLE_SCOPE_INVALID` | 400 | Unknown action, scope not allowed for the action, or a duplicate action |
| `ROLE_DEPENDENCY_MISSING` | 400 | §4.2. Properties: `action`, `requires` |
| `ROLE_NAME_INVALID` | 400 | Blank, or longer than 100 characters; description longer than 280 |
| `ROLE_NAME_FIXED` | 400 | Name or description sent for a Built-in role |
| `ROLE_NAME_TAKEN` | 409 | Name clashes with another role in the company or with a Built-in name |
| `ROLE_LIMIT_REACHED` | 409 | A 31st custom role |
| `ROLE_CHANGED` | 409 | Stale `version` |
| `ROLE_NOT_BUILT_IN` | 400 | Restore on a custom role |
| `ROLE_BUILT_IN_UNDELETABLE` | 400 | Delete on a Built-in role |
| `ROLE_REPLACEMENT_REQUIRED` | 409 | Delete of a held role without `replacement` |
| `ROLE_REPLACEMENT_INVALID` | 400 | Replacement is the same role, the Owner role or unknown |

`ROLE_ABOVE_CALLER` and `ROLE_OWN` need a coded 403. Today `AccessDeniedException` always maps to `FORBIDDEN`. Add `shared/exception/ForbiddenRuleException(code, message)` mapped to 403 with its code. Plain `require()` failures keep `FORBIDDEN`.

## 6. Built-in role definitions and startup sync

### 6.1 Definition file `construx/src/main/resources/built-in-roles.yml`

It replaces `seeded-roles.properties`.

```yaml
# Built-in roles every company has, besides Owner. Edit, restart, done (ADR 0010).
# Codes are permanent: never rename one; remove it and add a new one instead.
owner:            # names only: Owner always holds every permission
  name: { en: Owner, es: Propietario }
  description: { en: "…", es: "…" }
roles:
  - code: ADMINISTRATOR
    name: { en: Administrator, es: Administrador }
    description: { en: "…", es: "…" }
    grants:
      MANAGE_ROLES: ORGANIZATION
      MANAGE_MEMBERS: ORGANIZATION
      # …
```

Load rules (each one fails the boot):
- The code matches `[A-Z][A-Z0-9_]{0,63}`, is not `OWNER` and does not start with `CUSTOM_`.
- No duplicate codes.
- Names are 1 to 100 characters in both languages, and the EN and ES names are unique across all Built-in roles.
- Grants pass §4.

The current grants of the 7 roles carry over unchanged. EN names are copied from the dashboard's `rolesMessages`; descriptions are new copy.

### 6.2 Sync (`BuiltInRoleSync`, runs on `ApplicationReadyEvent`, one transaction, idempotent)

_As shipped:_ the event fires after the server starts listening, so on the very first boot after `V41` requests can briefly reach companies the sync has not reached yet (missing `RESIDENT` / `SITE_MANAGER` / `SUPERINTENDENT`, an Owner without a new action). Later boots only differ while a changed file is being applied. Every role the sync changes gets its `version` raised by one, so an editor holding the old version gets `ROLE_CHANGED`.

For every company:
1. **Owner:** ensure it holds every catalog action at `ORGANIZATION`. This replaces the Owner part of future backfills.
2. **For each role in the file:**
   - If the company lacks it, create it with the defaults, `customized = false`, and every catalog action marked known.
   - If the company has a custom role with that code (a Built-in role removed earlier and now re-added), adopt it: set `seeded = true` and `customized = true`, clear `description`, keep its permissions, and mark every catalog action known. Audit `ADOPT`.
   - If it exists and `customized = false`, set its permissions to exactly the defaults.
   - If it exists and `customized = true`, add the default grant for each catalog action not yet known to the role (if the default grants it). Then validate the result against §4. If the result is invalid, leave that action out and log a warning naming the company, role and action.
   - In every case, set the stored `name` to the file's ES name unless that clashes with a custom role name in that company (then keep the old one and log a warning), and mark every catalog action known.
3. **For each Built-in role in the database whose code is no longer in the file:** convert it to a custom role (`seeded = false`, `customized = false`, `description` null). Members, invitations, permissions, stored name and code are unchanged. Audit `CONVERT_TO_CUSTOM`. A converted role may take a company past 30 custom roles; the limit applies only to creating roles.
4. **Audit:** one `SYNC` event per role whose permissions or name actually changed (actor null, before/after permission sets). Nothing is audited when nothing changed.

New companies get the Owner role plus every Built-in role, created by the same code path as step 2.

### 6.3 Migration of existing data

`V41` adds the columns and the table and nothing else. All existing Built-in roles start `customized = false` with no known actions. On the first boot, step 2 brings them to the file and records the known actions. The three roles added after some companies were created (`RESIDENT`, `SITE_MANAGER`, `SUPERINTENDENT`) get created where they are missing; this closes v1-api §10 Q5. No custom roles exist yet, because there was no endpoint to create one.

## 7. Audit events

Through `AuditService.record`:
- Entity `ORGANIZATION_ROLE` (entityId = role id), actions `CREATE`, `UPDATE`, `RESTORE`, `DELETE`, `SYNC`, `ADOPT`, `CONVERT_TO_CUSTOM`. Before/after: `{ code, name, description, permissions }`.
- Entity `ORGANIZATION_MEMBERSHIP` (entityId = membership id), action `ROLE_CHANGE`. Before/after: `{ roleCode }`.
- A delete with a replacement records one `ROLE_CHANGE` per moved membership plus `DELETE`.

The actor is the caller's membership id, or null for the sync.

## 8. Dashboard

### 8.1 Navigation

- The sidebar entry "Team / Equipo" becomes the group **People / Personal**, with sub-items **Members / Miembros** (`/members`) and **Roles & permissions / Roles y permisos** (`/members/roles`).
- The group shows when the caller holds `MANAGE_MEMBERS` or `MANAGE_ROLES` at `ORGANIZATION` scope. Members shows with `MANAGE_MEMBERS`, Roles & permissions with either.
- On phones (`workspace-tabbar`) there is one tab, **People / Personal**, and both pages show a tab strip at the top. The strip is hidden when only one sub-page is visible.
- The breadcrumb section for `/members` and `/members/roles…` is **People / Personal**.

### 8.2 Roles & permissions page (`/members/roles`)

A list of roles, each with its display name in the current language, a kind badge (Owner / Built-in / Custom, plus "Customized" when `customized`), the member count and a short description. Actions: "New role" (with `MANAGE_ROLES` and fewer than 30 custom roles), and "Duplicate" on any role whose permissions fit within the caller. A role opens `/members/roles/:code`.

### 8.3 Role page (`/members/roles/:code`)

**Permissions tab**
- Grouped by catalog group. One row per action: name, description, and a segmented control limited to the allowed scopes, with None added.
- Read-only when `editable = false`, with a one-line reason (Owner is locked / your own role / holds permissions you don't have).
- Switching a permission on also switches on what it requires at the minimum scope, with an inline note ("Also turned on: View plans").
- Switching a requirement off, or lowering it, also switches off or lowers whatever depends on it, after a confirm listing them.
- A role with no permissions shows a warning: "Members with this role can sign in but see nothing."
- Save sends 5.4. `ROLE_CHANGED` reloads the role with a notice.
- Built-in roles show "Restore defaults", with a confirm that previews the differences from `defaults`.
- Custom roles show name and description fields and "Delete role", which opens a dialog. If the role is held, the dialog requires a replacement chosen from the assignable roles and states how many members and invitations will move.

**People tab** (only with `MANAGE_MEMBERS`)
- The members holding this role (5.7), each with a role dropdown (assignable roles only).
- "Add person": a picker of company members whose current role and this role are both assignable by the caller.
- The caller's own row is shown without a dropdown.

### 8.4 Members page

Each member row gets a role dropdown listing the assignable roles. It is disabled for the Owner, for the caller, and for members whose current role is not assignable. The invite form lists only assignable roles.

### 8.5 Labels and caching

- Role display names come from `names[locale]` on whatever role summary the screen already has (5.11). `roleLabel(role, locale)` returns `role.names?.[locale] ?? role.name`. `rolesMessages` and the per-code lookup are removed. Its callers are `CompanySwitcher`, `MembersPage`, `InviteForm`, `ProfilePage`, `SitePeople` and `SiteOverviewTab`.
- Permission names and descriptions come from the catalog.
- New UI strings go in `features/roles/messages.ts` (EN and ES).
- After any role write or assignment, refetch `GET /roles`. Refetch the caller's own `GET /me` when they return to the tab and on route change, so a change takes effect without a reload (D9).
- _As shipped (#106):_ `GET /me` is refetched at most once every 30 s, so a change can take up to 30 s (or a tab return) to show in the caller's menu. The server applies it on the next request regardless.

## 9. Acceptance cases

1. An Administrator creates "Foreman with prices" from Worker plus `VIEW_PRICES`, and assigns a Worker to it. That member now sees what `VIEW_PRICES` gates; before, they did not. _As shipped:_ the prices endpoints were removed with the catalog services, so `VIEW_PRICES` gates the financial document folders (their entries go from 404 to 200) and the Prices entry in the dashboard menu.
2. An Administrator sends a POST with `MANAGE_BUDGET:ORGANIZATION` and gets 403 `ROLE_ABOVE_CALLER`. The Owner sending the same request gets 201.
3. An Administrator sends a PUT to the Finance role and gets 403 `ROLE_ABOVE_CALLER`. The Finance role shows `editable: false` to them.
4. An Administrator sends a PUT to the Administrator role (their own) and gets 403 `ROLE_OWN`. The Owner can.
5. An Administrator patches a member into Finance and gets 403. Patching a member who is currently in Finance into Worker also gets 403.
6. An Administrator invites someone as Finance and gets 403 `ROLE_ABOVE_CALLER`.
7. A PUT of `MANAGE_PLAN:PROJECT` without `VIEW_PLAN` gets 400 `ROLE_DEPENDENCY_MISSING` with `action=MANAGE_PLAN` and `requires=VIEW_PLAN`.
8. A PUT of `VIEW_PRICES:PROJECT` gets 400 `ROLE_SCOPE_INVALID`.
9. The Owner removes `MANAGE_PLAN` from Member in company A. Member is `customized: true` in A and unchanged in company B. Restore in A brings back the file grants and `customized: false`.
10. A developer adds `VIEW_PRICES: ORGANIZATION` to WORKER in the file and restarts. Company B's (uncustomized) Worker gains it. Company A's customized Worker does not, because `VIEW_PRICES` is already known.
11. A new action `X` is added to the catalog with a WORKER default. After restart both A's customized Worker and B's Worker hold `X`, and custom roles do not.
12. RESIDENT is removed from the file. After restart, existing Resident roles are custom roles with the same members and permissions, and new companies have no Resident.
13. A role is renamed in the file (EN and ES). After restart the dashboard shows the new names in both languages with no dashboard change.
14. Deleting a custom role held by 3 members without a replacement gets 409 `ROLE_REPLACEMENT_REQUIRED` with `memberCount=3`. A custom role referenced only by a former (`LEFT`) member also needs a replacement, with `memberCount=0` and `formerMemberCount=1`. With `replacement=WORKER` it gets 204, and the 3 members are Workers.
15. The 31st custom role gets 409 `ROLE_LIMIT_REACHED`.
16. Two admins edit the same role. The second save gets 409 `ROLE_CHANGED`.
17. A member whose role was just edited loses the action on the very next request, with no re-login.
18. A Worker opens `/members/roles` and is redirected away. The sidebar shows no People group.
